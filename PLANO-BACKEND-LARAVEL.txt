------------------------------------------------------------------------------------
0. SUMARIO EXECUTIVO
------------------------------------------------------------------------------------

    O frontend foi construido, de proposito, contra um contrato REST completo e
    coeso (DTOs + endpoints + handlers mock) que HOJE e servido por MSW (Mock
    Service Worker) no browser, simulando exactamente o comportamento que um
    backend Laravel real deve ter — paginacao, filtros, ordenacao, validacao,
    codigos de erro, e a logica de workflow (processos, missoes, avaliacoes,
    documentos). Construir o backend Laravel e, por isso, um exercicio de
    IMPLEMENTAR um contrato ja especificado, nao de o desenhar do zero.

    ACTUALIZACAO (pos-Fase 2): a excepcao da AUTENTICACAO foi fechada. O modulo
    de login/registo/recuperacao de senha (Login.tsx, Registar.tsx,
    RecuperarSenha.tsx, RedefinirSenha.tsx, Perfil.tsx, useAuth.tsx,
    useUserRole.tsx) e mais 3 componentes que ainda falavam directamente com o
    Supabase (NotificationCenter.tsx, GlobalSearch.tsx, ChatWidget.tsx) foram
    todos migrados para a mesma camada services/api + MSW do resto da app —
    ver `src/services/api/auth.ts` + `src/mocks/handlers/auth.ts` (contrato
    completo, Seccao 2) e `src/mocks/handlers/chatAssistant.ts` (Seccao 2.5).
    `@supabase/supabase-js` foi desinstalado e `src/integrations/supabase/`
    apagado — o frontend HOJE nao tem nenhuma dependencia de Supabase, nem em
    build-time nem em runtime. Autenticacao continua a ser DESENHADA DE RAIZ em
    Laravel (Sanctum) do lado do backend real — nao existe uma tabela Supabase
    de referencia 1:1 como existe para os restantes ~44 dominios — mas o
    CONTRATO que o Laravel tem de replicar ja esta implementado e testado no
    mock (ver Seccao 2.2), nao apenas especificado em prosa.

    Este plano cobre: arquitectura Laravel, autenticacao/RBAC, modelo de dados
    completo (~44 dominios), mapeamento de rotas, regras de negocio dos 4
    workflows com maquina de estados (Processos, Missoes, Avaliacoes,
    Documentos), armazenamento de ficheiros, notificacoes, geracao de PDF,
    seeders, ambiente/deployment, e um plano de execucao faseado que espelha
    a ordem dos grupos da Fase 2 do frontend (para paridade incremental e
    testes modulo-a-modulo).

1. ARQUITECTURA GERAL
------------------------------------------------------------------------------------

  1.1 STACK
      - Laravel 11.x (PHP 8.3+), API-only (sem Blade/Inertia — o frontend e
        SPA separado, servido pelo Vite/Nginx).
      - Base de dados: PostgreSQL 15+ (mantém paridade com o Postgres que o
        Supabase original usava — os DTOs ja assumem tipos Postgres-friendly:
        arrays em `tags`/`roles`/`departmentIds`, JSON em `payload`).
      - Autenticacao: Laravel Sanctum, modo SPA (cookie-based, `sanctum/csrf-cookie`
        + sessao) — NAO tokens Bearer, para que o comportamento de sessao seja
        equivalente ao que o Supabase Auth ja dava (sessao persistente,
        refresh silencioso, sem gestao manual de tokens no frontend).
      - Autorizacao: Gates/Policies do Laravel, alimentados pela tabela
        `role_permissions` (ver 2.3) — replica exactamente `src/lib/permissions.ts`.
      - Filas/Jobs: Laravel Queue (database ou Redis) para: envio de emails
        (recuperacao de senha, notificacoes), geracao de relatorios pesados,
        recalculo de agregados do dashboard.
      - Cache: Redis (ou file em dev) para a matriz de permissoes (equivalente
        ao cache em memoria de `useUserRole.tsx`) e para agregados do BI.
      - Armazenamento: Laravel Filesystem, disco `public` em dev, S3-compatible
        (ex: MinIO/DigitalOcean Spaces) em producao — ver Seccao 6.
      - API Resources (`JsonResource`) em TODOS os endpoints de leitura, para
        garantir a conversao snake_case -> camelCase e a forma exacta dos DTOs
        (nunca devolver modelos Eloquent crus).
      - Form Requests (`FormRequest`) em TODOS os endpoints de escrita, para
        validacao — os campos obrigatorios/opcionais estao documentados nos
        `*Input`/`*Payload` de cada DTO.
      - i18n: o frontend já trata toda a apresentacao (PT/EN); o backend so
        precisa devolver mensagens de erro de validacao em portugues por
        omissao (`config/app.php` locale `pt`) — nao ha necessidade de um
        pacote de traducao no Laravel.

  1.2 ESTRUTURA DE PASTAS (sugerida)
      app/
        Models/                  (~44 modelos, 1 por tabela principal)
        Http/
          Controllers/Api/       (1 controller por recurso, RESTful)
          Resources/             (1 Resource por DTO)
          Requests/              (1 FormRequest por *Input/*Payload)
          Middleware/
            EnsureModulePermission.php   (substitui o RoleGuard do frontend
                                           no lado servidor — 403 se
                                           !canView(role, module))
        Policies/                (1 Policy por recurso com regras write)
        Services/
          ProcessWorkflowService.php     (maquina de estados de Processos)
          MissionWorkflowService.php     (submeter/aprovar/rejeitar)
          EvaluationWorkflowService.php  (avaliacoes: submeter/aprovar/
                                           rejeitar/validar/reabrir)
          DocumentWorkflowService.php    (rascunho->submetido->aprovado)
          PermissionMatrixService.php    (cache da matriz role_permissions)
        Notifications/
        Jobs/

  1.3 VERSIONAMENTO DA API
      Prefixo `/api` (sem versao no path — o frontend já assume isto via
      `VITE_API_URL`). Se uma quebra de contrato for necessária no futuro,
      introduzir `/api/v2` apenas para os recursos afectados, mantendo v1
      para o resto (nao versionar tudo de uma vez).

2. AUTENTICACAO E AUTORIZACAO (desenhado de raiz — sem tabela Supabase de origem)
------------------------------------------------------------------------------------

  2.1 O QUE O FRONTEND JA FAZ HOJE (implementado contra o mock — ver
      `src/services/api/auth.ts` + `src/mocks/handlers/auth.ts`; consumido por
      Login.tsx, Registar.tsx, RecuperarSenha.tsx, RedefinirSenha.tsx,
      Perfil.tsx, useAuth.tsx, useUserRole.tsx)
      - Login por email + password (`POST /login`). Contas demo mantidas
        (admin@iiv.demo / admin123, e equivalentes para tecnico/gestor/
        diretor/colaborador — password mock = `<primeiro papel>123`).
      - Registo cria conta com papel "colaborador" por omissao, SEM
        confirmacao por email (o mock nao implementa `MustVerifyEmail` —
        decisao a confirmar com o produto antes do Laravel real; se for
        necessario, e um acrescento ao contrato, nao uma mudanca).
      - Recuperar senha: pedido de reset por email (`POST /forgot-password`);
        o mock gera um token e um link `/redefinir-senha?token=...&email=...`
        (sem envio real de email, o link e impresso na consola em modo DEV —
        `console.info`). O Laravel real substitui isto por Laravel Mail.
      - Redefinir senha: RedefinirSenha.tsx LÊ `token`/`email` da QUERYSTRING
        do link (`useSearchParams`), NAO de uma sessao Supabase no hash da
        URL como na versao antiga — `POST /reset-password { token, email,
        password }`.
      - Mudar password (autenticado): Perfil.tsx usa
        `PATCH /user/password { password }` — rota nova, nao existia na
        versao anterior deste documento (era feita via `supabase.auth.
        updateUser`, sem equivalente REST explicito).
      - Sessao: `useAuth` expoe `{ user, loading, signOut, refresh }`, onde
        `user` e directamente um `UserDto` (sem `session` separado — o
        Supabase `User`/`Session` desapareceram). No arranque da app e apos
        login/registo, chama `GET /user` para hidratar/recarregar o estado.
      - Logout: `POST /logout` + limpa o token local.

      IMPORTANTE (mock vs. alvo real): como o MSW nao consegue definir
      cookies httpOnly reais de forma fiável em todos os cenarios de teste,
      o mock aproxima a sessao com um TOKEN SIMPLES (`= user.id`) devolvido
      no corpo do login/registo e guardado em `localStorage`
      (`AUTH_TOKEN_STORAGE_KEY` em `src/lib/http.ts`), reenviado como
      `Authorization: Bearer <token>` em cada pedido (ver interceptor de
      `http.ts`). ISTO NAO E O DESENHO ALVO — o Laravel real deve continuar a
      implementar Sanctum SPA cookie-based (ver 2.2 e 2.4), tal como ja
      estava planeado; quando essa integracao acontecer, o injector de
      `Authorization` em `http.ts` deixa de ser necessario
      (basta remover esse bloco do interceptor — o cookie viaja sozinho via
      `withCredentials: true`) e pode ser removido sem qualquer outra
      mudanca no frontend.

  2.2 ROTAS DE AUTENTICACAO
      GET   /sanctum/csrf-cookie   (fora do prefixo /api — obrigatorio antes
                                     do 1º POST, padrao Sanctum SPA; SEM
                                     equivalente no mock actual, que nao usa
                                     cookies — ver nota acima)
      POST  /api/login             { email, password } -> 204 + cookie sessao
                                     (mock: 200 + { token, user })
      POST  /api/logout             -> 204
      POST  /api/register          { fullName, email, password,
                                     password_confirmation } -> 201
                                     (mock: 201 + { user }, papel "colaborador")
      POST  /api/forgot-password   { email } -> 204 (sempre 204 mesmo se o
                                     email nao existir — nao revelar)
      POST  /api/reset-password    { token, email, password,
                                     password_confirmation } -> 204
      PATCH /api/user/password     { password } -> 204 (autenticado; muda a
                                     propria password — rota nova, ver 2.1)
      GET   /api/user               -> UserDto do utilizador autenticado
                                       (mesma forma do resource /api/users/{id},
                                       agora incluindo `email`)

  2.3 TABELAS
      users
        id (uuid), full_name, email (unique), phone (nullable),
        password (hash), email_verified_at, remember_token, timestamps
        -> substitui profiles + auth.users do Supabase original.
      user_roles                  (pivot; um user pode ter >1 papel —
        user_id (fk users), role (enum: admin|diretor|gestor|tecnico|
                 colaborador), timestamps                — a UI (useUserRole)
        so usa o primeiro por ordem alfabetica quando ha varios, mas o
        schema permite multiplos por design).
        IMPORTANTE: `GET /user` tem de devolver `roles` JA CONSOLIDADO no
        `UserDto` (array, resolvido via eager-load de `user_roles`) — o
        frontend (`useUserRole.tsx`, funcao `primaryRole()` em
        `src/lib/permissions.ts`) deriva o papel principal directamente de
        `user.roles` e NAO faz nenhum pedido separado a um endpoint de
        "papel do utilizador actual"; nao criar um.
      user_departments             (pivot)
        user_id (fk users), department_id (fk departments)
      role_permissions
        id, role (enum AppRole), module (string — ver ModuleKey em
        src/lib/permissions.ts para a lista fechada dos ~38 valores validos,
        idealmente validada por enum/check constraint), can_view (bool),
        can_write (bool)
        -> alimenta PermissionMatrixService::forRole($role), com cache
           (equivalente a ensurePermissionsLoaded() do frontend). Seed
           inicial = tabela ROLE_PERMISSIONS estatica de permissions.ts,
           1 linha por (role, module).

  2.4 MIDDLEWARE / POLICIES
      - `auth:sanctum` em TODAS as rotas `/api/*` excepto as publicas
        (ver Seccao 4.1) e as de auth.
      - `EnsureModulePermission:{module}` (route middleware parametrizado)
        substitui o `<RoleGuard module="...">` do frontend do lado servidor
        — sem isto, um utilizador pode contornar o RoleGuard client-side
        com um pedido HTTP directo. Aplicar a TODAS as rotas de escrita
        (POST/PUT/PATCH/DELETE) e, quando o modulo for sensivel, tambem a
        leitura.
      - Admin tem sempre `canView`/`canWrite` = true (mesma regra hardcoded
        de `canView()`/`canWrite()` em permissions.ts — nao depender so da
        tabela para o admin, e um safety net deliberado no frontend a manter).

  2.5 ASSISTENTE (CHAT) — desenhado de raiz, sem tabela Supabase de origem
      `ChatWidget.tsx` (renderizado so dentro de `AdminLayout.tsx` — feature
      exclusivamente autenticada) falava directamente com uma Supabase Edge
      Function (`supabase/functions/chat-assistant/index.ts`, que faz proxy
      para um modelo de LLM). Foi migrado para:

        POST /api/chat-assistant   { messages: [{ role, content }] }
                                    -> stream SSE (Content-Type:
                                    text/event-stream), 1 chunk por token/
                                    fragmento, formato OpenAI-like:
                                      data: {"choices":[{"delta":
                                        {"content":"..."}}]}\n\n
                                    ...
                                      data: [DONE]\n\n

      Middleware: `auth:sanctum` (rota so usada por utilizadores autenticados
      no admin; nao expor publicamente).

      O mock (`src/mocks/handlers/chatAssistant.ts`) devolve uma resposta
      fixa em streaming simulado (sem LLM real) — serve para validar que o
      cliente (parser SSE em `ChatWidget.tsx`, linhas de leitura de
      `ReadableStream`) funciona, mas NAO substitui a integracao real. O
      Laravel tem de implementar esta rota como proxy para um provedor de
      LLM (ex: OpenAI, Anthropic, ou o mesmo provedor que a Edge Function
      Supabase original usava — consultar
      `supabase/functions/chat-assistant/index.ts`, mantido no repo como
      referencia), devolvendo o streaming no MESMO formato SSE acima para
      nao obrigar a alterar `ChatWidget.tsx`. Sugestao de implementacao:
      `StreamedResponse` do Laravel com `Content-Type: text/event-stream` e
      flush incremental à medida que os chunks chegam do provedor de LLM.

4. ROTAS DA API — MAPEAMENTO DE src/services/api/endpoints.ts
------------------------------------------------------------------------------------

  4.1 ROTAS PUBLICAS (sem auth:sanctum) — consumidas pelo portal publico
      GET  /noticias, /noticias/{id}                 (so published=true)
      GET  /legislacao, /legislacao/{id}              (so published=true)
      GET  /hero-slides                               (so published=true)
      GET  /public/stats
      POST /contact-messages                          (criar, rate-limited)
      GET  /departamentos                              (usado no formulario
                                                          de registo/RH?
                                                          validar necessidade
                                                          de exposicao publica)

  4.2 ROTAS AUTENTICADAS (auth:sanctum + EnsureModulePermission)
      Para CADA entrada em `endpoints.ts` fora da lista 4.1: gerar as rotas
      RESTful equivalentes (index/store/show/update/destroy) MAIS as acoes
      nomeadas explicitas ja documentadas no ficheiro (ex: `archive`/`restore`
      em produtos; `advance`/`return`/`cancel` em processos; `submit`/
      `approve`/`reject` em missoes/avaliacoes). Usar `Route::apiResource`
      para o CRUD estandar e `Route::post/put` explicito para as acoes
      nomeadas, mantendo o path EXACTO do endpoints.ts (incluindo os termos
      em portugues: `/avancar`, `/devolver`, `/aprovar`, etc. — nao traduzir
      para ingles, o frontend chama estes paths literalmente).

      Modulos com paginacao (a maioria dos `list`): aceitar `page`, `perPage`,
      `search` e os filtros especificos de cada `*ListParams` do DTO;
      devolver sempre no formato de `PaginatedDto` (paginated.ts) —
      { data: T[], meta: { total, page, perPage, totalPages } } — este é o
      envelope que TODOS os hooks `use*List` do frontend esperam.

      NAO CRIAR um endpoint `/search` agregado: `GlobalSearch.tsx` (Cmd+K)
      NAO tem — nem precisa de — rota propria. Faz fan-out client-side,
      chamando em paralelo os `search` de cada `services/api/*.ts` ja
      migrado (produtos, lotes, laboratorios, documentos, processos, etc.,
      cada um com `perPage: 5`) e filtra client-side quando o modulo nao
      suporta `search` no servidor (caso de `contact-messages`, que so tem
      `page`/`perPage` — ver `ContactMessageListParams`). Se `search` estiver
      bem implementado em CADA endpoint individual (ponto acima), a pesquisa
      global funciona sem qualquer rota adicional.

      Auth e Assistente (Seccoes 2.2 e 2.5) NAO seguem o padrao RESTful
      indexado por recurso acima — sao rotas de accao pontual, ja mapeadas
      integralmente nessas seccoes.

  4.3 ACOES ESPECIAIS A REPLICAR EXACTAMENTE (efeitos colaterais no servidor)
      - POST /processos                -> gera `code` (ex: PRC-2026-0001),
        instancia process_steps a partir de process_type_steps, activa a
        1ª etapa, regista evento "aberto" (ver process.ts, comentarios).
      - POST /processos/{id}/avancar|devolver|cancelar -> maquina de estados
        completa (ver 5.1) — o cliente so envia `{ notes?, actorId? }`.
      - POST /missoes/{id}/submeter|aprovar|rejeitar -> transicoes de
        `MissionStatus` (ver 5.2).
      - POST /avaliacoes/{id}/submeter|aprovar|rejeitar|validar|reabrir ->
        maquina de estados mais rica (5 transicoes — ver 5.3).
      - PUT /documentos/{id} com mudanca de `status` -> workflow de aprovacao
        documental (5.4).
      - POST /produtos/{id}/archive|restore -> soft-toggle de `isActive`
        (unico modulo com este padrao — confirmar em produto.ts).

5. WORKFLOWS COM MAQUINA DE ESTADOS (a logica de negocio mais critica a portar)
------------------------------------------------------------------------------------

  5.1 PROCESSOS (process.ts) — motor BPM generico e reutilizavel
      Estados do processo: aberto -> em_curso -> concluido | cancelado
      Estados de etapa:    pendente -> em_curso -> concluida | rejeitada | devolvida
      Regras:
        - Ao criar: copiar as `process_type_steps` do tipo escolhido para
          `process_steps` (na ordem `orderIndex`), 1ª etapa = em_curso,
          restantes = pendente; `currentStepId` = 1ª etapa; status = em_curso;
          gerar `code` sequencial por ano (PRC-{ano}-{seq:04d}).
        - `avancar`: conclui a etapa actual (completed_at = now), activa a
          etapa seguinte (em_curso, started_at = now) ou, se era a ultima,
          marca o processo `concluido` (closed_at = now); regista
          process_event tipo "avancado".
        - `devolver`: marca a etapa actual como "devolvida", reactiva a
          etapa anterior como "em_curso"; regista evento "devolvido".
        - `cancelar`: status = cancelado, closed_at = now, qualquer etapa
          em curso fica "rejeitada"; regista evento "cancelado".
        - Toda transicao grava `notes` e `actorId` no evento correspondente
          (ProcessEventDto.payload).
      Implementar como `ProcessWorkflowService` injectavel no Controller —
      nao logica inline, para poder ser testado isoladamente (ver Seccao 12).

  5.2 MISSOES (missoes.ts)
      planeada -> submetida -> aprovada -> em_curso -> concluida | cancelada
      - `submeter`: planeada -> submetida (exige guia de marcha e >=1
        participante? — confirmar regra exacta no handler mock
        `src/mocks/handlers/missoes.ts` antes de implementar).
      - `aprovar`/`rejeitar`: so a partir de "submetida".
      - Relatorio final (`ReportDto`) e um sub-recurso 0..1 com o seu proprio
        mini-workflow (rascunho -> submetido -> aprovado|rejeitado),
        independente do status da missao-mae.

  5.3 AVALIACOES DE DESEMPENHO (avaliacoes.ts)
      Workflow mais rico: submeter -> aprovar/rejeitar -> validar -> reabrir
      (5 acoes nomeadas em endpoints.ts). Levantar os estados exactos e as
      transicoes permitidas directamente em avaliacoes.ts + o handler mock
      correspondente antes de implementar — nao assumir uma maquina de
      estados linear sem confirmar `reabrir` (que provavelmente permite
      voltar atras a partir de um estado terminal, algo que a maioria dos
      outros workflows nao tem).

  5.4 DOCUMENTOS (documento.ts)
      rascunho -> submetido -> aprovado | rejeitado -> (arquivado, terminal
      a qualquer momento por um utilizador com permissao de escrita).
      Cada nova versao de ficheiro (`DocVersionDto`) incrementa
      `versionNumber` e actualiza `currentVersionId` no documento-pai;
      versoes antigas mantêm-se acessiveis (nao apagar).

------------------------------------------------------------------------------------

    - Notificacoes in-app (tabela `notifications`): geradas server-side por
      eventos de dominio (ex: processo atribuido a um utilizador, missao
      aprovada, documento rejeitado). Usar Laravel Notifications
      (`Notification::send`) com o canal `database` a escrever directamente
      na tabela ja no formato do `NotificationDto`.
    - Polling vs. tempo-real: CONFIRMADO — `NotificationCenter.tsx` e
      `Notificacoes.tsx` nao usam WebSockets nem Supabase Realtime (a
      subscricao `postgres_changes` que existia foi removida na migracao).

      useNotifications.ts`) com `refetchInterval: 15000` (React Query) —

      `GET /notifications` seja rapido o suficiente para polling frequente);
      Laravel Echo + Reverb/Pusher fica como evolucao futura opcional, nao
      bloqueante para o lancamento nem para paridade com o frontend actual.
