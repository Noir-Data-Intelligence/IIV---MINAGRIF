------------------------------------------------------------------------------------
0. SUMARIO EXECUTIVO
------------------------------------------------------------------------------------

    Este plano descreve a modernizacao completa do frontend do portal do IIV/MINAGRIF,
    sem alterar as regras de negocio nem os fluxos funcionais ja existentes. O
    objectivo e transformar um frontend funcional mas datado (acoplado directamente
    ao SDK do Supabase, sem tema activo, sem i18n, com ~30-40 blocos de codigo CRUD
    repetidos) num frontend profissional, animado, internacionalizado (PT/EN),
    com tema claro/escuro, e ja preparado para consumir um backend Laravel REST.

    O QUE NAO MUDA NO NEGOCIO:
    Todos os fluxos actuais mantem-se — motor BPM de processos, avaliacoes de
    desempenho, missoes (submissao/aprovacao/guia de marcha/prestacao de contas),
    laboratorio, producao, qualidade, financeiro, RH, investigacao/BI, etc. Nao ha
    supressao de funcionalidade. O que muda e a CAMADA de apresentacao, a CAMADA de
    acesso a dados e a CAMADA de autenticacao — nao a logica de dominio.

    CORRECCAO DE EXPECTATIVA (IMPORTANTE):
    O pedido inicial mencionava "paginas inacabadas para terminar". Apos levantamento
    exaustivo, linha a linha, de todas as ~41 paginas de administracao, 11 paginas
    publicas e 4 paginas de autenticacao, NAO foi encontrada NENHUMA pagina vazia,
    placeholder ou "em breve". Todas tem CRUD real, validacao e, em varios casos,
    workflows sofisticados. O trabalho real NAO e "terminar paginas por fazer"; e:
      (a) MODERNIZAR a UI/UX (tema, animacao, tabelas, formularios, gráficos);
      (b) DESACOPLAR do Supabase e preparar para Laravel REST (via mock primeiro);
      (c) CORRIGIR pequenos problemas de conteudo/dados (ver Seccao 4);
      (d) RESOLVER gaps de escala (paginacao server-side, agregacoes pesadas).
    Este documento reflecte essa realidade para gerir expectativas com transparencia.

    REMOCAO TOTAL DE LOVABLE E DE SUPABASE (IMPORTANTE):
    Dois requisitos adicionais, tratados como obrigatorios em todo o plano, nao como
    "nice to have":
      (i)  REMOVER toda e qualquer dependencia do LOVABLE (plataforma que gerou o
           projecto originalmente): pasta .lovable/, dependencia npm "lovable-tagger"
           e o respectivo plugin no vite.config.ts, README.md reescrito de raiz (hoje
           e o boilerplate generico do Lovable), URLs "*.lovable.app" hardcoded
           (sitemap.xml, robots.txt, SEO.tsx, Index.tsx), e a Edge Function
           "chat-assistant" que hoje depende do "Lovable AI Gateway" (variavel
           LOVABLE_API_KEY) — ver detalhe completo em 1.10 e 4.8.
      (ii) O BACKEND FINAL E 100% LARAVEL. Isto vai alem de "preparar para consumir"
           uma API Laravel: o objectivo declarado e a DESCONTINUACAO TOTAL do
           Supabase (Postgres/RLS, Auth, Storage, Realtime e Edge Functions) — nao
           apenas do SDK supabase-js no frontend. A fase de MOCK (MSW) e uma etapa
           intermedia de desenvolvimento, nao um destino; o destino e sempre o
           Laravel REST real (ver Fase 4, Seccao 6).

3. ARQUITECTURA ALVO
------------------------------------------------------------------------------------

  ================================================================================
  3.1 CAMADA DE DADOS / API (MOCK AGORA -> LARAVEL REST DEPOIS)
  ================================================================================

    3.1.1 PRINCIPIO ORIENTADOR
        Hoje ha ~41 pontos de acoplamento directo ao SDK Supabase espalhados por
        useEffect/handlers. A estrategia e introduzir UMA camada de acesso a dados
        entre os componentes e a origem de dados, para que a troca Supabase -> mock
        -> Laravel se faca num unico sitio, sem tocar nos componentes.

        Fluxo alvo:
          Componente/Pagina
            -> hook de dominio (react-query: useNoticias(), useMissoes(), ...)
              -> servico de modulo (services/api/noticias.ts)
                -> client HTTP unico (lib/http.ts, axios/ky com interceptors)
                  -> [MSW intercepta em dev/mock]  ou  [Laravel REST em producao]

    3.1.2 ESTRUTURA DE PASTAS PROPOSTA
        src/
          lib/
            http.ts                 -- client HTTP unico (axios ou ky) + interceptors
            queryClient.ts          -- config do @tanstack/react-query
          services/
            api/
              client.ts             -- re-export do http + helpers (get/post/put/del)
              endpoints.ts          -- mapa central de rotas REST (contrato)
              noticias.ts           -- CRUD noticias (list/get/create/update/remove)
              legislacao.ts
              missoes.ts
              laboratorio.ts
              producao.ts
              qualidade.ts
              financeiro.ts
              rh.ts
              investigacao.ts
              processos.ts
              documentos.ts
              utilizadores.ts
              rbac.ts
              ...                   -- um ficheiro por modulo/recurso
          types/
            dto/                    -- DTOs/tipos partilhados (contrato com Laravel)
              noticia.ts
              missao.ts
              paginated.ts          -- envelope generico { data, meta:{page,total} }
              ...
          hooks/
            queries/                -- hooks react-query por dominio
              useNoticias.ts
              useMissoes.ts
              ...
          mocks/                    -- MSW (Fase 0..3)
            browser.ts              -- setupWorker
            server.ts               -- setupServer (para testes)
            handlers/
              index.ts
              noticias.ts
              missoes.ts
              ...
            fixtures/               -- dados ficticios (seed)
              noticias.json
              missoes.json
              ...

    3.1.3 CLIENT HTTP UNICO (lib/http.ts)
        - Base: axios (recomendado; ecossistema de interceptors maduro) ou ky (mais
          leve, fetch-based). Recomendacao: AXIOS pela familiaridade com interceptors
          de token/refresh e por integrar bem com Sanctum (withCredentials).
        - Configuracao:
            * baseURL a partir de import.meta.env.VITE_API_URL.
            * withCredentials: true (necessario para Sanctum cookie-based).
            * Interceptor de request: injectar header Authorization Bearer (se modo
              token) ou nada (se modo cookie SPA) + header X-Requested-With.
            * Interceptor de response: tratamento central de 401 (logout/refresh),
              419 (CSRF/sessao expirada Sanctum), 422 (mapear erros de validacao
              Laravel para react-hook-form), 403 (sem permissao -> toast + UX), 5xx.
            * Normalizacao do envelope de paginacao Laravel ({data, meta, links}).

    3.1.4 CONTRATO DE ENDPOINTS POR MODULO (endpoints.ts)
        Definir um mapa central, versionado, base para o backend Laravel. Convencao
        REST por recurso (plural, kebab/snake conforme decisao de equipa). Exemplos:

          GERAL
            GET    /api/noticias?page=&per_page=&search=&status=
            POST   /api/noticias
            GET    /api/noticias/{id}
            PUT    /api/noticias/{id}
            DELETE /api/noticias/{id}
            (identico para legislacao, hero-slides, mensagens, notificacoes,
             utilizadores, departamentos)
            GET    /api/rbac/roles
            GET    /api/rbac/permissions
            PUT    /api/rbac/permissions            -- matriz papel x modulo

          LABORATORIO
            /api/laboratorios, /api/analises, /api/resultados, /api/insumos

          PRODUCAO
            /api/produtos, /api/lotes, /api/planeamento, /api/distribuicao

          QUALIDADE
            /api/estacoes, /api/auditorias, /api/nao-conformidades, /api/animais,
            /api/inseminacao/{centros|reprodutores|tanques}, /api/logs

          RECURSOS & PRODUCAO
            /api/stock/{itens|localizacoes|movimentos}, /api/agricultura,
            /api/producao-pecuaria

          GESTAO
            /api/documentos (+ /versions, /permissions), /api/processos (+ /etapas)

          FINANCEIRO & PATRIMONIO
            /api/contas, /api/orcamentos, /api/activos, /api/manutencoes

          PESSOAS & MISSOES
            /api/rh/colaboradores, /api/missoes (+ /aprovar, /guia-marcha,
            /prestacao-contas), /api/formacoes

          INVESTIGACAO & BI
            /api/linhas-pesquisa, /api/publicacoes, /api/avaliacoes (+ /aprovar),
            /api/bi/institucional

          AUTH (ver 3.2)
            POST /api/login, POST /api/logout, GET /api/user,
            GET /sanctum/csrf-cookie (se cookie-based)

        NOTA: Agregacoes de KPI (Financeiro/Stock/Patrimonio/Dashboard/BI) devem ter
        endpoints dedicados de resumo no Laravel (ex: GET /api/financeiro/resumo) para
        eliminar a agregacao client-side pesada actual (ver gap 1.7).

    3.1.5 DTOs / TIPOS PARTILHADOS
        - Um DTO por recurso em src/types/dto/, que representa o contrato exacto do
          JSON REST (camelCase no frontend; se o Laravel devolver snake_case, mapear
          numa camada de (de)serializacao no servico ou usar API Resources Laravel em
          camelCase — decisao a alinhar com a equipa backend).
        - Envelope generico Paginated<T> = { data: T[]; meta: { currentPage, perPage,
          total, lastPage } }.
        - Estes tipos devem, sempre que possivel, derivar dos MESMOS schemas zod usados
          nos formularios (z.infer<typeof schema>) para garantir contrato unico entre
          formulario, validacao e REST (ver 3.7).

    3.1.6 ESTRATEGIA DE MOCK: MSW (RECOMENDADO) vs FIXTURES
        - RECOMENDACAO: MSW (Mock Service Worker). Intercepta ao nivel da rede (Service
          Worker no browser / setupServer em testes), o que significa que o client HTTP,
          interceptors, react-query e tratamento de erros sao exercitados de forma
          IDENTICA ao futuro Laravel. A troca mock->real e literalmente desligar o
          worker e apontar VITE_API_URL para o backend. Vantagem decisiva sobre uma
          fake-API em memoria (que nao exercita a camada HTTP).
        - Handlers em src/mocks/handlers/ replicam o contrato de 3.1.4, servindo dados
          de src/mocks/fixtures/ (JSON com dados ficticios realistas do dominio IIV:
          nomes de missoes, lotes de vacinas, resultados de analises, etc.).
        - Fixtures podem ser seed inicial exportado/derivado dos dados actuais do
          Supabase (opcional) para realismo.
        - Controlo por env: VITE_API_MOCK=true activa o worker; =false usa Laravel.

    3.1.7 PLANO DE MIGRACAO SUPABASE -> LARAVEL, MODULO A MODULO
        Passo A (preparacao, sem trocar backend): centralizar TODAS as chamadas
          supabase-js dentro dos servicos de modulo (services/api/*.ts). Nesta fase os
          servicos ainda chamam supabase por dentro, mas os componentes ja so conhecem
          o hook/servico. Isto isola o acoplamento em ~41 -> N ficheiros de servico.
        Passo B: introduzir react-query nos hooks de dominio (cache, loading, erro,
          invalidacao) substituindo useEffect+useState manuais.
        Passo C: reimplementar cada servico contra o client HTTP + MSW (mock). Trabalhar
          modulo a modulo, comecando pelos mais simples (Noticias, Legislacao,
          Departamentos) e terminando nos complexos (Missoes, Processos, BI).
        Passo D (quando o Laravel existir, OBRIGATORIO, nao opcional): desligar MSW,
          apontar VITE_API_URL para o backend real, ajustar apenas (de)serializacao/
          edge-cases. Componentes e hooks nao mudam. Este passo inclui, para alem das
          tabelas de dados:
            * STORAGE: os buckets Supabase (noticias, legislation, documents,
              hero-slides, avatars) passam a ser servidos por um disco de ficheiros
              Laravel (local ou S3-compativel) via endpoints proprios de upload/
              download (ex: POST /api/uploads, URLs assinadas quando aplicavel).
            * REALTIME: LiveStats, NotificationCenter, timeline de Processos e
              Documentos usam hoje supabase.channel()/postgres_changes. Substituir
              por: (a) polling com refetchInterval do react-query (mais simples,
              suficiente para a maioria dos casos), ou (b) WebSockets via Laravel
              Reverb/Pusher + Laravel Echo (para notificacoes verdadeiramente
              instantaneas). Decidir por caso de uso (ver D12, Seccao 9).
            * EDGE FUNCTIONS: "chat-assistant" (hoje usa o Lovable AI Gateway, ver
              1.10/4.8) e "send-transactional-email" tornam-se endpoints/jobs
              Laravel — o chat chama directamente um provedor de LLM (OpenAI/
              Anthropic, chave propria do cliente), o email usa Laravel Mail/queues.
            * SUPABASE-JS: remover a dependencia @supabase/supabase-js do frontend
              por completo assim que o ultimo modulo migrar (ver Seccao 7).
          Nao existe estado final de coexistencia Supabase+Laravel — o Supabase e

  3.2 AUTENTICACAO & RBAC (SUPABASE AUTH -> SANCTUM/JWT)
  ================================================================================

    3.2.1 SITUACAO ACTUAL
        - useAuth.tsx = wrapper fino sobre supabase.auth (onAuthStateChange/getSession/
          signOut). Sessao em localStorage via supabase-js.
        - Autorizacao REAL = RLS do Postgres. A RBAC em JS e apenas UX.

    3.2.2 ESTRATEGIA DE AUTENTICACAO ALVO (LARAVEL SANCTUM)
        Duas opcoes Sanctum; recomendar decidir com a equipa backend:
          OPCAO A — SPA cookie-based (RECOMENDADA para SPA no mesmo dominio/subdominio):
            * Fluxo: GET /sanctum/csrf-cookie -> POST /api/login (email/senha) -> cookie
              de sessao httpOnly. Requests subsequentes com withCredentials:true.
            * Vantagens: token nunca exposto a JS (mitiga XSS), CSRF gerido por Sanctum.
            * Requisitos: SPA e API em dominios compativeis (config CORS + SANCTUM
              stateful domains no Laravel).
          OPCAO B — Token-based (Bearer) (para dominios distintos / mobile futuro):
            * POST /api/login devolve token pessoal; guardar com cuidado (de preferencia
              em memoria + refresh; evitar localStorage por XSS).
            * Interceptor injecta Authorization: Bearer.
        Para o portal (SPA web institucional), OPCAO A e a mais segura e simples.

    3.2.3 O QUE MUDA NO FRONTEND
        - Reescrever useAuth.tsx para falar com o client HTTP (login/logout/getUser)
          em vez de supabase.auth. Manter a MESMA interface publica do hook (user,
          session, signIn, signOut, loading) para minimizar impacto nas paginas.
        - AuthProvider carrega GET /api/user no arranque (hidratacao da sessao).
        - Paginas de auth (Login/Registar/RecuperarSenha/RedefinirSenha) trocam as
          chamadas signInWithPassword/signUp/resetPasswordForEmail/updateUser por
          endpoints REST equivalentes (POST /api/login, /api/register,
          /api/forgot-password, /api/reset-password).
        - Tratamento de 401/419 no interceptor -> redireccionar para /login.

    3.2.4 O QUE TEM DE SER REIMPLEMENTADO NO BACKEND (CRITICO)
        - O RLS do Postgres DESAPARECE ao sair do Supabase. A autorizacao REAL tem de
          passar a ser feita no Laravel: Policies/Gates por recurso e/ou middleware por
          modulo+papel, validando can_view/can_write no servidor para CADA endpoint.
        - A matriz de permissoes (role_permissions) e os defaults (permissions.ts) devem
          ser replicados/migrados para o backend como fonte de verdade de autorizacao.

    3.2.5 O QUE SE MANTEM NO FRONTEND
        - Os hooks de RBAC de frontend (useUserRole, RoleGuard, WriteGuard proposto)
          MANTEM-SE como camada de UX (esconder nav/botoes, bloquear rotas), desde que
          o backend valide TUDO de novo. O frontend nunca e a fronteira de seguranca.
        - A pagina RBAC (matriz Papel x Modulo) passa a ler/gravar via /api/rbac/*.

8. RISCOS E MITIGACOES
------------------------------------------------------------------------------------

    R1  Autorizacao real depende do RLS Supabase; ao migrar, o RLS desaparece.
        MITIGACAO: reimplementar autorizacao no Laravel (Policies/Gates/middleware) —
        3.2.4. Nunca confiar na RBAC de frontend como fronteira de seguranca.

    R2  Migracao dos ~41 pontos de acoplamento Supabase e extensa e propensa a regressao.
        MITIGACAO: faseamento modulo a modulo (3.1.7), do simples ao complexo; MSW
        garante contrato identico ao Laravel; testar cada modulo antes de avancar.

    R3  Contrato REST divergir da implementacao real do Laravel (snake vs camel,
        paginacao, formatos de erro).
        MITIGACAO: fixar cedo o contrato (endpoints.ts + DTOs + envelope Paginated),
        alinhar com a equipa backend ANTES da Fase 4; usar API Resources Laravel.

    R4  i18n em ~55 paginas e trabalhoso e sujeito a strings esquecidas.
        MITIGACAO: extraccao faseada por area; i18next-parser para detectar chaves em
        falta/orfas; PT como fallback garante que nada "parte" se faltar traducao.

    R5  Dark mode pode expor contrastes maus (cores hardcoded, glass/backdrop-blur).
        MITIGACAO: auditoria de contraste sistematica (3.4.2); forcar uso de tokens HSL;
        validar WCAG AA nos dois temas.

    R6  Animacoes podem degradar performance (tabelas grandes) ou acessibilidade.
        MITIGACAO: motion com proposito (3.5.3); respeitar prefers-reduced-motion;
        nao animar linhas de tabelas grandes.

    R7  Regressao na auditoria de acessibilidade existente (Acessibilidade.tsx/axe-core).
        MITIGACAO: correr axe-core apos cada fase; incluir a11y na definicao de "pronto".

    R8  Complexidade dos modulos pesados (Missoes ~757 linhas, Processos BPM, BI).
        MITIGACAO: deixar para o fim da ordem de migracao; abstraccoes ja maduras e
        testadas nos modulos simples antes de os atacar.

    R9  Dependencias de conteudo do cliente (dominio real, logotipos, URLs sociais).
        MITIGACAO: recolher cedo (Seccao 9); nao bloquear implementacao tecnica por isso.

    R10 Media Pexels — licenca/adequacao cultural.
        MITIGACAO: verificar licenca Pexels; curadoria com contexto angolano; logotipos
        oficiais vem do cliente, nao de bancos de imagem.

    R11 Descomissionamento do Supabase e mais do que trocar o SDK: Storage, Realtime
        e Edge Functions (chat-assistant no Lovable AI Gateway, send-transactional-
        email) precisam de equivalente funcional no Laravel antes do "apagar" final.
        MITIGACAO: mapear cada servico Supabase para o seu equivalente Laravel logo
        na Fase 0/3.1.7 (disco de ficheiros, polling/Reverb, Mail/jobs, chamada a LLM
        proprio); nao apagar nada em producao antes do equivalente estar validado.

    R12 Chat assistant perde o backend actual (Lovable AI Gateway) ao remover Lovable/
        Supabase; sem substituicao, a funcionalidade de chat desaparece.
        MITIGACAO: decidir cedo o provedor de LLM proprio (D11) e orcar a
        reimplementacao como parte da Fase 4, nao como detalhe tardio.
